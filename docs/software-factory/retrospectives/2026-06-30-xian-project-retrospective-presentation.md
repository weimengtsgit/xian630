# 西安 630 项目软件工厂复盘汇报结构

本文基于《西安 630 项目软件工厂复盘提纲》整理为内部汇报材料结构，面向产品与交付决策层。建议做成 15 页左右 PPT，控制在 20-30 分钟汇报。

## 汇报主线

本次汇报不要把 630 项目讲成一次普通交付总结，而要讲清楚三件事：

1. 客户通过这次现场表达了怎样的软件工厂理解口径。
2. 电子云这次实际验证了哪些闭环能力，以及还有哪些客户高感知短板。
3. 电子云软件工厂未来应如何围绕多 agent 协作、领域能力沉淀和云产品深度结合形成产品主张。

## 1. 封面

标题：西安 630 项目软件工厂复盘

副标题：从客户理解口径到电子云软件工厂产品主张

讲述口径：

本次复盘不是简单回顾现场演示效果，而是把客户对软件工厂的理解、我们本次验证的能力、以及后续产品化方向放在一起看，形成下一阶段软件工厂建设判断。

## 2. 一句话结论

页面核心信息：

630 现场交付验证了电子云软件工厂在“自然语言到应用生成、本体数据接入、客户系统嵌入”上的最小闭环，也证明客户高度关注需求澄清、数据流转、协作过程和最终应用效果；但这只是客户对软件工厂的一种高价值理解，电子云软件工厂的长期主张应是以多 agent 管理协作、任务分发执行、领域能力包沉淀为核心，并与 DevOps、低代码、微服务、网关、观测等云产品深度结合，形成可持续进化的软件生产体系。

讲述口径：

这句话需要同时表达成绩和边界。成绩是最小闭环已验证；边界是客户这次的理解不能等同于我们未来产品终局。

## 3. 三层复盘框架

页面要点：

- 第一层：客户理解口径。客户希望看到自然语言、多轮澄清、多 agent 协作、真实数据接入和应用生成。
- 第二层：本次交付验证。电子云证明了自然语言到应用、本体数据接入、真实数据展示和客户系统嵌入的闭环。
- 第三层：电子云软件工厂产品主张。长期核心是多 agent 管理协作、任务分发执行、领域能力包沉淀和云产品能力底座融合。

讲述口径：

这三层必须分开。客户口径是重要输入，但不是全部产品定义；交付验证说明我们当前站在哪里；产品主张回答下一步往哪里走。

## 4. 客户理解口径：客户真正关心什么

页面要点：

- 需求理解与澄清：准确理解业务场景，主动提出澄清项，持续让用户确认。
- 数据接入与数据流转：讲清数据来源、处理过程、进入 agent/LLM 的方式和应用展示结果。
- 方案设计可控：关键方案可人工调整，不由模型黑箱主导。
- 多 agent 协作可视化：执行前看协作图，执行中看状态、产物、失败重试。
- 最终应用质量：界面效果好，真实数据驱动，贴合客户系统，可嵌入。
- 自我进化与能力沉淀：能沉淀 agent、skills 和过往经验。

讲述口径：

客户不是只看“能不能生成代码”，而是看软件工厂能不能把需求、数据、协作和最终应用全过程讲清楚、做出来、可确认。

## 5. 客户场景暴露的能力要求

页面要点：

客户提供的航母母港潮汐、甲板风、商船密度、开源社区异常、舰载机归属推断、航母活动复盘等场景，共同暴露出五类能力要求：

- 强领域业务理解。
- 外部数据源、本体数据或开源数据接入。
- 规则、阈值、时间窗口、空间关系、置信度等客户判断口径转应用逻辑。
- 地图、仪表盘、时间线、关系树、告警等复杂前端表达。
- 场景经验后续沉淀为领域能力包。

讲述口径：

这些场景不建议逐个讲细节，重点是说明它们不是普通页面生成需求，而是领域知识、数据接入和应用表达能力的综合测试。

## 6. 本次电子云交付验证了什么

页面要点：

- 自然语言描述生成应用的整体流程跑通。
- 本体数据源已对接。
- 生成应用能够调用本体数据源展示真实数据。
- 界面样式贴合客户系统。
- 生成应用具备嵌入客户系统的便利性。

页面结论：

电子云已经从“生成 demo 页面”推进到“面向客户系统的真实数据应用生成”。

讲述口径：

这次最重要的验证不是某个页面，而是自然语言、真实数据、应用生成和系统嵌入之间的闭环已经成立。

## 7. 现场厂商观察

页面表格：

| 厂商 | 现场表现 | 客户可能感知到的优势 |
| --- | --- | --- |
| 领铄 | 成品软件形态较完整，Web 端操作，体验类似通用智能体产品 | 需求分析交互、澄清项识别、数据源处理过程可视化更容易被客户感知 |
| 电子云 | 自然语言到应用生成闭环跑通，对接本体真实数据，界面贴合客户系统 | 真实数据应用生成闭环、客户系统嵌入能力、与电子云产品结合空间 |
| 15 所 | 后端服务封装 Claude Code，通过终端跑流程，需手动启动查看结果 | 工程链路直接，但产品化展示和用户体验不足 |

讲述口径：

不要讲厂商输赢，而要讲客户认可能力差距。领铄让客户更容易看到“过程可信”，电子云证明了“闭环可用”。

## 8. 从闭环可用到过程可信

页面要点：

电子云下一步需要把闭环可用升级为：

- 过程可信：需求澄清、数据流转、agent 协作过程可见。
- 产物稳定：生成应用质量、真实数据接入、部署验证更稳定。
- 能力可沉淀：领域经验、skills、subagent、应用蓝本可复用。
- 工程可进入：agent 产物进入 DevOps、低代码、微服务、网关、观测等工程系统。

讲述口径：

闭环可用解决“能不能做出来”；过程可信和能力沉淀解决“客户是否信任、下一次能否更快更稳”。

## 9. 电子云软件工厂产品主张

页面核心图建议：

中心放“多 agent 管理协作与任务分发执行”，周围四类能力：

- 领域能力包沉淀。
- Agent/Skills 市场。
- 云产品能力底座。
- 软件工厂工作台。

页面要点：

电子云软件工厂不应被定义为单次应用生成工具，也不应被定义为云产品的 AI 包装层。

长期主张是：以多 agent 管理协作、任务分发执行、领域能力包沉淀为核心，通过 agent、skills、subagent 的持续扩展和高度编排，结合自身云产品完成真实工程生产。

讲述口径：

应用生成是入口，但不是终局。软件工厂真正的产品对象是 agent、skills、subagent、任务、编排、领域知识和产物。

## 10. Agent 组织方式

页面标题：默认生产主链路 + 动态扩展专业 agent

页面要点：

- 默认生产主链路：需求分析、测试设计、方案设计、代码生成、测试生成、测试验证、代码审查、部署交付、观测回写。
- 动态扩展专业 agent：领域知识 agent、系统集成 agent、数据接入 agent、安全审查 agent、低代码 agent、网关集成 agent、微服务 agent、观测 agent。
- 协作编排 agent：根据用户需求、客户领域、系统环境和交付目标选择 agent、安排依赖、分发任务、汇总产物。

讲述口径：

未来软件工厂不能是固定 agent 流水线，而应允许不断补充 agent。客户领域不同、系统环境不同、交付目标不同，参与计划就应该不同。

## 11. Agent 与 Skills 市场

页面要点：

- 协作智能体市场：发现、分发、安装和治理 agent 能力，包括内置 agent、行业 agent、系统集成 agent、客户自定义 agent。
- Skills 市场：发现、分发、安装和治理 skills，包括领域知识、工具调用方法、云产品适配、代码生成规范、数据接口契约。
- 本地能力库：当前租户或项目已安装、启用、可进入任务参与计划的能力资产。

第一阶段轻量可演示范围：

- 展示 agent 和 skills 列表。
- 展示版本、来源、适用场景、权限和工具边界。
- 支持把某个 agent 或 skill 加入一次任务参与计划。
- 暂不做公开发布、计费、评分和复杂审核流。

讲述口径：

市场解决能力持续扩展和分发问题，库解决本地可用和治理问题。这个能力证明软件工厂不是固定内置 agent，而是可以持续成长。

## 12. 领域能力包沉淀

页面要点：

每交付一类场景，都应沉淀为领域能力包：

- 领域知识。
- 数据接口契约。
- 判断规则和研判参数。
- skills。
- subagent。
- 应用蓝本。
- 验收口径。
- 可观测指标。

讲述口径：

客户场景越多，不应该意味着每次从零开始。软件工厂应通过领域能力包变成“越交付越强”的系统。

## 13. 云产品能力底座与交互场景

页面要点：

软件工厂会与电子云自身云产品深度结合，形成云产品交互场景：

- DevOps：需求、任务、代码仓库、流水线、制品、部署记录。
- 低代码：表单、流程、报表、管理页面。
- 微服务：服务接口、注册、治理和调用。
- 网关：API 暴露、鉴权、限流和路由。
- 观测：日志、指标、链路追踪、告警和质量看板。

讲述口径：

云产品不是被 AI 包装，而是成为 agent 可以调用、写入、消费、治理和观测的能力底座。软件工厂的价值在于让 agent 工作进入真实工程生产链路。

## 14. 第一阶段优先闭环：DevOps

页面标题：先打通 DevOps，证明 agent 进入软件生产主链路

页面要点：

DevOps 第一阶段最小闭环：

1. 需求分析 agent 生成需求规格说明书，并拆成 DevOps 需求项/任务项。
2. 测试设计 agent 根据需求项生成测试用例，并写入 DevOps 测试管理能力。
3. 代码生成 agent 在对应项目仓库提交代码。
4. 测试生成 agent 在代码生成后生成自动化测试脚本。
5. 测试验证/部署 agent 触发或更新流水线。
6. 部署结果、制品地址、应用访问地址回写 DevOps。
7. 软件工厂工作台反向展示 DevOps 链接和状态。

讲述口径：

DevOps 是第一阶段最优先打通对象，因为它承接软件生产主链路。只要这个闭环跑通，软件工厂就不是独立 demo 工具，而是进入企业工程系统。

## 15. 客户高感知能力建设优先级

页面要点：

客户现场感知优先级建议：

1. 数据流转可视化。
2. 需求澄清与推荐收敛。
3. 多 agent 协作执行图与状态。
4. 生成应用效果和嵌入能力。
5. 自我进化与 skills 沉淀展示。

讲述口径：

数据流转可视化优先级最高。客户最容易质疑的是数据是否真实、数据怎么来、怎么处理、怎么进入分析、最终怎么展示。数据链路讲清楚，多 agent 和生成应用才更可信。

## 16. 关键技术边界

页面要点：

必须区分生成期数据链路和运行期数据链路：

- 生成期数据链路：需求澄清、数据接入、接口验证、字段抽取、数据契约、下游生成约束。
- 运行期数据链路：生成应用通过 API、网关、本体服务、代理、鉴权配置获取真实数据，并负责展示、刷新和降级。

技术边界：

factory-server 不应成为所有业务应用的通用数据查询网关。软件工厂负责生成期数据边界、数据契约和运行期访问逻辑生成；运行期真实数据访问由生成应用结合 API、网关、本体服务或代理机制完成。

讲述口径：

这个边界决定系统职责是否可控。否则软件工厂后端会逐渐变成承接所有业务数据访问的中台，产品边界会失控。

## 17. 非目标和边界

页面要点：

- 不把 630 客户口径等同于电子云软件工厂终局。
- 不把软件工厂做成固定 agent 流水线。
- 不把软件工厂做成单纯应用 demo 生成器。
- 不把云产品融合写成 AI 包装。
- 不把 factory-server 做成所有业务数据的通用查询网关。

讲述口径：

这些不是消极限制，而是产品边界。边界越清楚，后续投入越不容易跑偏。

## 18. 下一阶段建议

页面标题：双线推进

页面要点：

客户高感知演示能力：

- 数据流转可视化。
- 需求澄清与推荐收敛。
- 多 agent 协作执行图与状态。
- 生成应用效果和嵌入能力。
- 自我进化与 skills 沉淀展示。

内部产品主轴能力：

- agent、subagent、skills 管理。
- agent 市场、Skills 市场和本地能力库。
- 任务分发、编排、执行、重试和评估。
- 领域能力包沉淀和选择。
- DevOps 第一阶段闭环打通。
- agent 运行观测、产物质量评估和执行复盘。

讲述口径：

这两条线要并行。只做演示能力，容易变成更漂亮的 demo 工具；只做主轴能力，短期现场客户不一定感知得到。

## 19. 需要决策的问题

页面要点：

- 第一阶段产品边界：先定义哪些能力进入软件工厂工作台。
- DevOps 最小闭环：确认需求项、测试用例、代码仓库、测试脚本、流水线、部署记录是否作为第一阶段必做。
- 市场能力范围：确认 agent 市场和 Skills 市场先做轻量可演示版。
- 数据流转可视化：确认作为下一次客户演示第一优先级。
- 领域能力包：确认以本次航母相关场景作为首批沉淀样本。

讲述口径：

汇报最后不要只停在观点，应推动形成下一阶段建设决策。
