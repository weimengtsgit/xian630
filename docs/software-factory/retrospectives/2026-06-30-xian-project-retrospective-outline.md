# 西安 630 项目软件工厂复盘提纲

本文面向内部产品与交付决策层，用于复盘 630 现场交付反映出的客户理解口径、电子云本次验证结果，以及电子云软件工厂后续产品化方向。

## 一句话结论

630 现场交付验证了电子云软件工厂在“自然语言到应用生成、本体数据接入、客户系统嵌入”上的最小闭环，也证明客户高度关注需求澄清、数据流转、协作过程和最终应用效果；但这只是客户对软件工厂的一种高价值理解，电子云软件工厂的长期主张应是以多 agent 管理协作、任务分发执行、领域能力包沉淀为核心，并与 DevOps、低代码、微服务、网关、观测等云产品深度结合，形成可持续进化的软件生产体系。

## 1. 复盘边界

本次复盘不把 630 客户口径等同于电子云软件工厂的完整产品定义。

客户理解口径是本次项目中的重要产品证据：客户希望通过自然语言、多轮澄清、多 agent 协作、真实数据接入和应用生成，完成具体业务场景的快速交付。

电子云软件工厂产品主张更宽：核心是多 agent 管理协作、任务分发执行、领域知识沉淀、skills/subagent 扩展，以及与 DevOps、低代码、微服务、网关、观测等云产品深度结合。

## 2. 客户理解口径

客户本次关注的软件工厂形态，可以概括为“从业务场景自然语言描述到真实数据驱动应用生成”的闭环。

客户认为软件工厂应具备以下能力：

1. 需求理解与澄清  
   准确理解领域业务场景，展示 agent 决策过程，主动推荐澄清项，并通过多轮确认收敛需求。

2. 数据接入与数据流转  
   说明数据从哪里来、如何处理、如何进入 agent/LLM 分析、最终如何在应用中展示。

3. 方案设计可控  
   方案设计阶段允许人为调整，避免完全由模型黑箱主导。

4. 多 agent 协作可视化  
   执行前展示多 agent 协作流程，执行中查看每个 agent 的运行状态、产出物、失败重试和调整入口。

5. 最终应用质量  
   生成应用必须界面效果好、对接真实数据、贴合客户系统，并方便嵌入客户现有系统。

6. 自我进化与能力沉淀  
   能从历史执行经验中沉淀 agent/skills，并在后续任务中自主判断和调用合适能力。

客户现场提供的七个航母相关场景不建议在正文逐个展开，而应作为附录或证据使用。正文重点抽象这些场景共同暴露的软件工厂能力要求：领域性强、依赖外部数据源或本体/开源数据、需要把规则/阈值/时间窗口/空间关系/置信度等客户判断口径转成应用逻辑，并要求地图、仪表盘、时间线、关系树、告警等高质量前端表达。这些场景适合作为后续领域能力包沉淀来源。

## 3. 本次交付验证

本次 630 大屏演示中，电子云已经证明了以下闭环能力：

- 自然语言描述生成应用的整体流程跑通。
- 已对接本体数据源。
- 生成应用能够调用本体数据源并展示真实数据。
- 生成应用界面样式贴合客户系统。
- 生成应用具备嵌入客户系统的便利性。

这些能力说明电子云已经从“生成 demo 页面”推进到“面向客户系统的真实数据应用生成”。

## 4. 友商演示观察

本次现场已演示的软件工厂产品包括领铄、电子云和 15 所。

| 厂商 | 现场表现 | 客户可能感知到的优势 |
| --- | --- | --- |
| 领铄 | 成品软件形态较完整，体验类似 opencode、Codex 通用智能体，Web 端操作 | 需求分析交互、澄清项识别、数据源处理过程可视化更容易被客户感知 |
| 电子云 | 自然语言到应用生成闭环跑通，对接本体真实数据，界面贴合客户系统 | 真实数据应用生成闭环、客户系统嵌入能力、与电子云产品结合空间 |
| 15 所 | 后端服务封装 Claude Code，通过终端跑流程，需手动启动查看应用结果 | 工程链路直接，但产品化展示和用户操作体验不足 |

复盘中不应写成厂商输赢，而应写成客户认可能力差距。领铄更容易让客户看到“过程可信”；电子云本次更明确证明了“闭环可用”。下一阶段需要把闭环可用升级为过程可信、产物稳定、能力可沉淀。

## 5. 电子云软件工厂产品主张

电子云软件工厂不应被定义为单次应用生成工具，也不应被定义为 DevOps、低代码、微服务等产品的 AI 包装层。

长期主轴应是：

- 多 agent 管理协作。
- 任务分发与执行。
- agent、skills、subagent 的持续沉淀和复用。
- 协作 agent 可按客户领域、目标系统、交付目标和集成需要持续补充。
- 客户领域知识沉淀为领域能力包。
- 通过高度编排满足不同领域客户的生产需求。
- 与自身云产品深度结合，把 agent 工作落入真实工程生产链路。

软件工厂的核心对象是 agent、skills、subagent、任务、编排、领域知识和产物。DevOps、低代码、微服务、网关、观测等云产品，是 agent 可以调用、写入、消费、治理和观测的云产品能力底座。

未来协作 agent 不应被固定为一条不可变流水线。除默认软件生产主链路外，软件工厂应能根据客户领域补充领域知识智能体，根据客户系统对接需要补充系统集成智能体，根据测试左移需要补充测试设计智能体和测试生成智能体，并在任务参与计划中明确每个 agent 的职责、输入、产物和依赖关系。

建议把未来 agent 组织方式定义为“默认生产主链路 + 动态扩展专业 agent”：

- 默认生产主链路负责通用软件生产：需求分析、测试设计、方案设计、代码生成、测试生成、测试验证、代码审查、部署交付、观测回写。
- 动态扩展专业 agent 按任务补充：领域知识 agent、系统集成 agent、数据接入 agent、安全审查 agent、低代码 agent、网关集成 agent、微服务 agent、观测 agent 等。
- 协作编排 agent 根据用户需求、客户领域、系统环境和交付目标，选择 agent、安排依赖、分发任务、汇总产物。

## 6. 领域能力包沉淀

不同客户、不同领域会带来更多场景，但软件工厂不能依赖每次临时写 prompt 或复制 demo 应用支撑。

每交付一类场景，都应沉淀为领域能力包，包括：

- 领域知识。
- 数据接口契约。
- 判断规则和研判参数。
- skills。
- subagent。
- 应用蓝本。
- 验收口径。
- 可观测指标。

未来 agent 编排应能根据客户领域和任务目标自动选择这些能力包，使软件工厂越交付越强。

## 7. Agent 与 Skills 市场

软件工厂内部应建设协作智能体市场和 Skills 市场，形成可持续扩展的能力生态。

协作智能体市场负责 agent 能力的发现和分发，承载内置 agent、行业 agent、系统集成 agent、客户自定义 agent 等。Skills 市场负责 skills 能力包的发现和分发，承载领域知识、工具调用方法、云产品适配、代码生成规范、数据接口契约等。

市场与库需要区分：

- 市场负责发现、安装、评价、版本、来源、适配领域、适配云产品、权限边界和治理审核。
- 库负责当前租户或项目已经安装、启用、可治理、可进入任务参与计划的本地能力资产。

这样软件工厂不会被限制为固定内置 agent，而是可以围绕客户领域、客户系统和云产品交互场景持续扩展。

第一阶段市场能力建议做轻量可演示版，不做完整生态市场：

- 能展示内置 agent、领域 agent、系统集成 agent。
- 能展示 skills、领域能力包、云产品适配 skill。
- 能把某个 agent 或 skill 加入一次任务参与计划。
- 能展示版本、来源、适用场景、权限/工具边界。
- 暂不做公开发布、计费、评分和复杂审核流。

## 8. 云产品交互场景

软件工厂与云产品的结合不是附属实现细节，而是一类一类工程生产场景。

典型云产品交互场景包括：

- 需求分析 agent 生成需求规格说明书，并把需求项录入 DevOps 平台。
- 代码生成 agent 在 DevOps 项目中创建或更新代码。
- 流水线 agent 触发构建、测试、制品生成和部署流水线。
- 微服务 agent 生成服务接口、注册服务、配置治理规则。
- 网关集成 agent 生成 API 暴露、鉴权、限流和路由配置。
- 低代码 agent 生成表单、流程、报表或管理页面。
- 观测 agent 配置日志、指标、链路追踪、告警和质量看板。

这些交互场景把 agent 的分析和生成能力转化为可治理、可审计、可运行的工程资产。

## 9. 关键技术边界

软件工厂需要清晰区分生成期职责和运行期职责。

在数据链路上，软件工厂负责在生成期确认数据来源边界、验证接口、形成数据契约，并生成运行期数据访问逻辑；但不应把 factory-server 定位为所有业务应用的通用数据查询网关。运行期真实数据应由生成应用通过 API、网关、本体服务或代理机制访问，并明确鉴权、刷新、降级和展示责任。

这个边界可以避免软件工厂后端逐渐变成承接所有业务数据访问的中台，导致产品职责失控。

## 10. 非目标和边界

复盘中需要明确以下边界，防止后续产品路线跑偏：

1. 不把 630 客户口径等同于电子云软件工厂终局。  
   本次客户理解口径是重要产品证据，但不是完整产品定义。

2. 不把软件工厂做成固定 agent 流水线。  
   默认生产主链路只是基础骨架，未来需要动态扩展领域、系统集成、数据、安全、低代码、网关、微服务、观测等专业 agent。

3. 不把软件工厂做成单纯应用 demo 生成器。  
   应用生成是重要入口，但长期核心是多 agent 管理协作、任务分发执行、领域能力包沉淀和工程生产闭环。

4. 不把云产品融合写成 AI 包装。  
   DevOps、低代码、微服务、网关、观测等云产品是 agent 可以调用、写入、消费、治理和观测的能力底座，目标是进入真实工程链路。

5. 不把 factory-server 做成所有业务数据的通用查询网关。  
   软件工厂负责生成期数据边界、数据契约和运行期访问逻辑生成，运行期真实数据访问应由生成应用结合 API、网关、本体服务或代理机制完成。

## 11. 产品化建议

下一阶段建议双线推进：一条线补齐客户高感知演示能力，另一条线建设内部产品主轴能力。前者决定现场认可度，后者决定软件工厂是否能成为长期产品，而不是更漂亮的 demo 工具。

### 11.1 客户高感知演示能力

优先级建议如下：

1. 数据流转可视化。  
   重点说明数据源从哪里来、如何处理、如何交给 agent/LLM 分析、如何形成数据契约、最终如何在应用中展示。这里必须区分生成期数据链路和运行期数据链路：生成期说明需求澄清、数据接入、接口验证、字段抽取、数据契约和下游生成约束；运行期说明生成应用如何通过 API、网关、本体服务、代理、鉴权配置等获取真实数据，并在界面展示、刷新和降级。

2. 需求澄清与推荐收敛。  
   强化需求理解、领域知识注入、推荐澄清项、多轮确认和高影响事项确认。

3. 多 agent 协作执行图与状态。  
   展示协作编排、agent 依赖、执行状态、产物、失败重试和调整入口。

4. 生成应用效果和嵌入能力。  
   提升 UI 质量、真实数据接入稳定性、客户系统风格贴合度和嵌入便利性。

5. 自我进化与 skills 沉淀展示。  
   展示历史执行经验如何沉淀为 agent、skills 或领域能力包，并在后续任务中被选择和复用。

### 11.2 内部产品主轴能力

- 建设 agent 管理、subagent 管理和 skills 管理。
- 建设协作智能体市场、Skills 市场和本地能力库。
- 建设任务分发、编排、执行、重试和评估机制。
- 建设领域能力包沉淀和选择机制。
- 建设 agent 运行过程观测、产物质量评估和执行复盘能力。
- 与 DevOps 打通需求、代码、流水线、制品和部署。
- 与低代码打通表单、流程、管理页面和可视化配置。
- 与微服务平台打通服务生成、注册、治理和调用。
- 与网关打通 API 暴露、鉴权、限流和路由。
- 与观测平台打通日志、指标、链路追踪、告警和质量度量。

第一阶段建议优先打通 DevOps 平台。DevOps 承接软件生产主链路，包括需求、任务、测试用例、代码仓库、分支、提交、测试脚本、流水线、制品和部署记录。软件工厂如果先把需求分析 agent、代码生成 agent、测试验证 agent、部署 agent 的产物写入 DevOps，就能证明它不是独立 demo 工具，而是在进入真实工程生产系统。

DevOps 第一阶段最小闭环建议限定为：

1. 需求分析 agent 生成需求规格说明书，并自动拆成 DevOps 需求项/任务项。
2. 测试设计 agent 根据需求项生成测试用例，并写入 DevOps 测试管理能力。
3. 代码生成 agent 在对应项目仓库提交代码。
4. 测试生成 agent 在代码生成后生成自动化测试脚本，并提交到项目仓库或关联到流水线。
5. 测试验证/部署 agent 触发或更新流水线。
6. 部署结果、制品地址、应用访问地址回写 DevOps。
7. 软件工厂工作台反向展示这些 DevOps 链接和状态。

## 12. 后续待展开问题

- 电子云软件工厂第一阶段产品边界如何定义。
- 先做通用 agent 编排平台，还是先做应用生成闭环增强。
- DevOps 第一阶段打通的最小闭环范围如何定义。
- 领域能力包的资产形态、版本管理、评估机制和复用机制如何设计。
- 客户现场演示应突出“过程可信”还是“最终应用效果”。
