# 西安 630 项目软件工厂复盘 PPT 文案

本文用于直接制作内部汇报 PPT。每页包含页面标题、页面主文案、建议视觉和讲稿备注。

## 1. 封面

页面标题：

西安 630 项目软件工厂复盘

页面副标题：

从客户理解口径到电子云软件工厂产品主张

页面信息：

- 汇报对象：内部产品与交付决策层
- 汇报目的：复盘现场验证结果，明确下一阶段产品化方向

讲稿备注：

本次汇报不只是回顾一次现场交付，而是把客户对软件工厂的理解、电子云本次验证的能力，以及后续产品化方向放在一起判断。

## 2. 一句话结论

页面标题：

本次交付验证了最小闭环，但不等于产品终局

页面主文案：

630 现场交付验证了电子云软件工厂在“自然语言到应用生成、本体数据接入、客户系统嵌入”上的最小闭环。

同时，客户高度关注需求澄清、数据流转、协作过程和最终应用效果。

但这只是客户对软件工厂的一种高价值理解。电子云软件工厂的长期主张，应是以多 agent 管理协作、任务分发执行、领域能力包沉淀为核心，并与 DevOps、低代码、微服务、网关、观测等云产品深度结合，形成可持续进化的软件生产体系。

建议视觉：

左侧“已验证闭环”，右侧“长期产品主张”，中间用箭头连接。

讲稿备注：

这页要先定调：我们承认本次现场证明了关键闭环，但不能把客户这次看到的软件工厂形态直接等同于电子云软件工厂未来完整形态。

## 3. 复盘框架

页面标题：

用三层框架看本次 630 项目

页面主文案：

第一层：客户理解口径  
客户希望软件工厂完成自然语言、多轮澄清、多 agent 协作、真实数据接入和应用生成。

第二层：本次交付验证  
电子云验证了自然语言到应用、本体数据接入、真实数据展示和客户系统嵌入。

第三层：产品主张  
电子云软件工厂长期核心是多 agent 管理协作、任务分发执行、领域能力包沉淀和云产品能力底座融合。

建议视觉：

三层金字塔或三段式横向结构。

讲稿备注：

这三层需要分开讲。客户口径是重要输入，但不是全部产品定义；交付验证说明我们当前站在哪里；产品主张回答下一步往哪里走。

## 4. 客户真正关心什么

页面标题：

客户关注的不是“能否生成代码”，而是全过程是否可信

页面主文案：

客户本次关注的软件工厂能力，可以归纳为六项：

- 需求理解与澄清：准确理解业务场景，主动提出澄清项，持续让用户确认。
- 数据接入与数据流转：讲清数据来源、处理过程、进入 agent/LLM 的方式和应用展示结果。
- 方案设计可控：关键方案可人工调整，不由模型黑箱主导。
- 多 agent 协作可视化：执行前看协作图，执行中看状态、产物和失败重试。
- 最终应用质量：界面效果好，真实数据驱动，贴合客户系统，可嵌入。
- 自我进化与能力沉淀：能沉淀 agent、skills 和过往经验。

建议视觉：

六宫格能力图。

讲稿备注：

客户不是单纯看“模型能不能写代码”，而是看软件工厂能不能把需求、数据、协作、产物和交付全过程讲清楚，并且每一步可确认。

## 5. 客户场景暴露的能力要求

页面标题：

七个航母相关场景，本质是在测试软件工厂的领域生产能力

页面主文案：

客户提供的场景包括潮汐窗口、甲板风、商船密度、开源社区异常、舰载机归属推断、航母活动复盘等。

这些场景共同暴露出五类能力要求：

- 强领域业务理解。
- 外部数据源、本体数据或开源数据接入。
- 规则、阈值、时间窗口、空间关系、置信度等客户判断口径转应用逻辑。
- 地图、仪表盘、时间线、关系树、告警等复杂前端表达。
- 场景经验后续沉淀为领域能力包。

建议视觉：

左侧列场景关键词，右侧归纳五类能力要求。

讲稿备注：

这些场景不建议逐个展开。重点是说明它们不是普通页面生成需求，而是领域知识、数据接入、规则研判和应用表达能力的综合测试。

## 6. 本次电子云验证了什么

页面标题：

电子云已经从 demo 页面推进到真实数据应用生成

页面主文案：

本次 630 大屏演示中，电子云证明了五项闭环能力：

- 自然语言描述生成应用的整体流程跑通。
- 本体数据源已对接。
- 生成应用能够调用本体数据源展示真实数据。
- 界面样式贴合客户系统。
- 生成应用具备嵌入客户系统的便利性。

页面结论：

这次最重要的验证不是某一个页面，而是“自然语言、真实数据、应用生成、系统嵌入”之间的闭环已经成立。

建议视觉：

自然语言输入 -> 需求澄清 -> 本体数据 -> 应用生成 -> 客户系统嵌入。

讲稿备注：

这里要强调成绩：我们不是只做了好看的静态页面，而是跑通了和本体真实数据、客户系统样式、系统嵌入有关的最小闭环。

## 7. 现场厂商观察

页面标题：

现场差异不应理解为厂商输赢，而应理解为客户认可能力差距

页面主文案：

| 厂商 | 现场表现 | 客户可能感知到的优势 |
| --- | --- | --- |
| 领铄 | 成品软件形态较完整，Web 端操作，体验类似通用智能体产品 | 需求分析交互、澄清项识别、数据源处理过程可视化更容易被客户感知 |
| 电子云 | 自然语言到应用生成闭环跑通，对接本体真实数据，界面贴合客户系统 | 真实数据应用生成闭环、客户系统嵌入能力、与电子云产品结合空间 |
| 15 所 | 后端服务封装 Claude Code，通过终端跑流程，需手动启动查看结果 | 工程链路直接，但产品化展示和用户体验不足 |

页面结论：

领铄更容易让客户看到“过程可信”；电子云本次更明确证明了“闭环可用”。

建议视觉：

三列对比表，突出“过程可信”和“闭环可用”两个关键词。

讲稿备注：

这页不要讲成谁赢谁输。对我们更有价值的是识别客户为什么认可：他们需要看到需求澄清过程、数据处理过程和 agent 协作过程。

## 8. 从闭环可用到过程可信

页面标题：

下一阶段要把“闭环可用”升级为“过程可信、产物稳定、能力可沉淀”

页面主文案：

电子云下一阶段需要补齐四个方向：

- 过程可信：需求澄清、数据流转、agent 协作过程可见。
- 产物稳定：生成应用质量、真实数据接入、部署验证更稳定。
- 能力可沉淀：领域经验、skills、subagent、应用蓝本可复用。
- 工程可进入：agent 产物进入 DevOps、低代码、微服务、网关、观测等工程系统。

建议视觉：

从“闭环可用”到四个升级方向的放射图。

讲稿备注：

闭环可用解决“能不能做出来”；过程可信和能力沉淀解决“客户是否信任、下一次能否更快更稳”。

## 9. 电子云软件工厂产品主张

页面标题：

软件工厂不是应用 demo 生成器，也不是云产品的 AI 包装层

页面主文案：

电子云软件工厂的长期主张：

以多 agent 管理协作、任务分发执行、领域能力包沉淀为核心，通过 agent、skills、subagent 的持续扩展和高度编排，结合自身云产品完成真实工程生产。

核心对象：

- agent
- skills
- subagent
- 任务
- 编排
- 领域知识
- 产物

能力支撑：

- 领域能力包沉淀。
- Agent/Skills 市场。
- 云产品能力底座。
- 软件工厂工作台。

建议视觉：

中心是“多 agent 管理协作与任务分发执行”，周围四个能力支撑。

讲稿备注：

应用生成是重要入口，但不是终局。真正的产品主轴是 agent 能力如何被管理、编排、分发、沉淀，并进入真实工程生产链路。

## 10. Agent 组织方式

页面标题：

默认生产主链路 + 动态扩展专业 agent

页面主文案：

默认生产主链路负责通用软件生产：

- 需求分析。
- 测试设计。
- 方案设计。
- 代码生成。
- 测试生成。
- 测试验证。
- 代码审查。
- 部署交付。
- 观测回写。

动态扩展专业 agent 按任务补充：

- 领域知识 agent。
- 系统集成 agent。
- 数据接入 agent。
- 安全审查 agent。
- 低代码 agent。
- 网关集成 agent。
- 微服务 agent。
- 观测 agent。

协作编排 agent 负责根据用户需求、客户领域、系统环境和交付目标选择 agent、安排依赖、分发任务、汇总产物。

建议视觉：

主链路横向流程 + 上方/下方可插拔专业 agent。

讲稿备注：

未来软件工厂不能是固定 agent 流水线。客户领域不同、系统环境不同、交付目标不同，参与计划就应该不同。

## 11. Agent 与 Skills 市场

页面标题：

市场负责能力发现和分发，库负责本地可用和治理

页面主文案：

协作智能体市场：

- 发现、分发、安装和治理 agent 能力。
- 承载内置 agent、行业 agent、系统集成 agent、客户自定义 agent。

Skills 市场：

- 发现、分发、安装和治理 skills。
- 承载领域知识、工具调用方法、云产品适配、代码生成规范、数据接口契约。

本地能力库：

- 当前租户或项目已经安装、启用、可治理、可进入任务参与计划的能力资产。

第一阶段轻量可演示范围：

- 展示 agent 和 skills 列表。
- 展示版本、来源、适用场景、权限和工具边界。
- 支持把某个 agent 或 skill 加入一次任务参与计划。
- 暂不做公开发布、计费、评分和复杂审核流。

建议视觉：

市场 -> 安装 -> 本地能力库 -> 任务参与计划。

讲稿备注：

市场能力能证明软件工厂不是固定内置 agent，而是可以持续成长、持续扩展、持续治理的能力体系。

## 12. 领域能力包沉淀

页面标题：

客户场景越多，软件工厂越应该沉淀能力，而不是每次从零开始

页面主文案：

每交付一类场景，都应沉淀为领域能力包：

- 领域知识。
- 数据接口契约。
- 判断规则和研判参数。
- skills。
- subagent。
- 应用蓝本。
- 验收口径。
- 可观测指标。

页面结论：

领域能力包让软件工厂从“一次性交付工具”变成“越交付越强的生产体系”。

建议视觉：

项目交付经验 -> 领域能力包 -> 后续任务自动选择和复用。

讲稿备注：

客户提供的航母相关场景，后续可以作为首批领域能力包沉淀样本。每个场景都不是一次性 prompt，而应该沉淀成可复用资产。

## 13. 云产品能力底座

页面标题：

云产品不是被 AI 包装，而是 agent 进入工程生产链路的能力底座

页面主文案：

软件工厂会与电子云自身云产品深度结合，形成云产品交互场景：

- DevOps：需求、任务、代码仓库、流水线、制品、部署记录。
- 低代码：表单、流程、报表、管理页面。
- 微服务：服务接口、注册、治理和调用。
- 网关：API 暴露、鉴权、限流和路由。
- 观测：日志、指标、链路追踪、告警和质量看板。

页面结论：

云产品能力底座让 agent 的分析和生成结果进入可治理、可审计、可运行的工程资产体系。

建议视觉：

上层 agent 编排，中层软件工厂工作台，下层 DevOps/低代码/微服务/网关/观测。

讲稿备注：

这页要避免把云产品讲成简单集成清单。关键是 agent 可以调用、写入、消费、治理和观测这些云产品，从而进入真实工程链路。

## 14. 第一阶段优先闭环：DevOps

页面标题：

先打通 DevOps，证明 agent 进入软件生产主链路

页面主文案：

DevOps 第一阶段最小闭环：

1. 需求分析 agent 生成需求规格说明书，并拆成 DevOps 需求项/任务项。
2. 测试设计 agent 根据需求项生成测试用例，并写入 DevOps 测试管理能力。
3. 代码生成 agent 在对应项目仓库提交代码。
4. 测试生成 agent 在代码生成后生成自动化测试脚本。
5. 测试验证/部署 agent 触发或更新流水线。
6. 部署结果、制品地址、应用访问地址回写 DevOps。
7. 软件工厂工作台反向展示 DevOps 链接和状态。

页面结论：

只要 DevOps 闭环跑通，软件工厂就不再是独立 demo 工具，而是进入企业软件生产系统。

建议视觉：

需求 -> 测试用例 -> 代码 -> 测试脚本 -> 流水线 -> 部署 -> 回写状态。

讲稿备注：

DevOps 是第一阶段最优先打通对象，因为它承接软件生产主链路，也最容易证明 agent 工作进入了企业工程体系。

## 15. 客户高感知能力优先级

页面标题：

下一次客户演示，第一优先级是数据流转可视化

页面主文案：

客户现场感知优先级建议：

1. 数据流转可视化。
2. 需求澄清与推荐收敛。
3. 多 agent 协作执行图与状态。
4. 生成应用效果和嵌入能力。
5. 自我进化与 skills 沉淀展示。

页面结论：

数据链路讲清楚，多 agent 和生成应用才更可信。

建议视觉：

优先级阶梯图，突出“数据流转可视化”。

讲稿备注：

客户最容易质疑的是数据是否真实、数据怎么来、怎么处理、怎么进入分析、最终怎么展示。因此数据流转可视化要先做强。

## 16. 关键技术边界

页面标题：

必须区分生成期数据链路和运行期数据链路

页面主文案：

生成期数据链路：

- 需求澄清。
- 数据接入。
- 接口验证。
- 字段抽取。
- 数据契约。
- 下游生成约束。

运行期数据链路：

- 生成应用通过 API、网关、本体服务、代理、鉴权配置获取真实数据。
- 应用负责展示、刷新、异常提示和降级。

技术边界：

factory-server 不应成为所有业务应用的通用数据查询网关。软件工厂负责生成期数据边界、数据契约和运行期访问逻辑生成；运行期真实数据访问由生成应用结合 API、网关、本体服务或代理机制完成。

建议视觉：

左右分栏：生成期链路 / 运行期链路。

讲稿备注：

这个边界决定系统职责是否可控。如果不区分，软件工厂后端很容易变成承接所有业务数据访问的中台，产品边界会失控。

## 17. 非目标和边界

页面标题：

明确不做什么，防止产品路线跑偏

页面主文案：

- 不把 630 客户口径等同于电子云软件工厂终局。
- 不把软件工厂做成固定 agent 流水线。
- 不把软件工厂做成单纯应用 demo 生成器。
- 不把云产品融合写成 AI 包装。
- 不把 factory-server 做成所有业务数据的通用查询网关。

页面结论：

这些不是消极限制，而是产品边界。边界越清楚，后续投入越不容易跑偏。

建议视觉：

五条边界清单，每条配一个简短图标。

讲稿备注：

这页要帮助内部形成一致认知。我们不是否定客户需求，而是把客户需求放进更大的产品主张里，同时明确哪些方向不能走偏。

## 18. 下一阶段建议

页面标题：

下一阶段建议双线推进

页面主文案：

客户高感知演示能力：

- 数据流转可视化。
- 需求澄清与推荐收敛。
- 多 agent 协作执行图与状态。
- 生成应用效果和嵌入能力。
- 自我进化与 skills 沉淀展示。

内部产品主轴能力：

- agent、subagent、skills 管理。
- agent 市场、Skills 市场和本地能力库。
- 任务分发、编排、执行、重试和评估。
- 领域能力包沉淀和选择。
- DevOps 第一阶段闭环打通。
- agent 运行观测、产物质量评估和执行复盘。

页面结论：

两条线要并行。只做演示能力，容易变成更漂亮的 demo 工具；只做主轴能力，短期现场客户不一定感知得到。

建议视觉：

双泳道路线图：客户高感知演示能力 / 内部产品主轴能力。

讲稿备注：

这页是行动建议，不是概念总结。演示能力解决近期客户认可，主轴能力解决长期产品成型。

## 19. 需要决策的问题

页面标题：

建议本次复盘后形成五项建设决策

页面主文案：

需要确认的决策：

1. 第一阶段产品边界：哪些能力进入软件工厂工作台。
2. DevOps 最小闭环：需求项、测试用例、代码仓库、测试脚本、流水线、部署记录是否作为第一阶段必做。
3. 市场能力范围：agent 市场和 Skills 市场是否先做轻量可演示版。
4. 数据流转可视化：是否作为下一次客户演示第一优先级。
