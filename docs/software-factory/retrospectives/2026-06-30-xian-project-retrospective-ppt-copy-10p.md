# 西安 630 项目软件工厂复盘 PPT 文案（10 页精简版）

本文是 10 页精简汇报稿，适合 10-15 分钟内部汇报。原 19 页版本保留为展开材料。

## 1. 封面与核心结论

页面标题：

西安 630 项目软件工厂复盘

页面副标题：

从客户理解口径到电子云软件工厂产品主张

页面主文案：

630 现场交付验证了电子云软件工厂在“自然语言到应用生成、本体数据接入、客户系统嵌入”上的最小闭环。

但这只是客户对软件工厂的一种高价值理解，不等于电子云软件工厂的产品终局。

电子云软件工厂长期主张应是以多 agent 管理协作、任务分发执行、领域能力包沉淀为核心，并与 DevOps、低代码、微服务、网关、观测等云产品深度结合，形成可持续进化的软件生产体系。

建议视觉：

左侧“630 已验证闭环”，右侧“长期产品主张”，中间用箭头连接。

讲稿备注：

开场先定调：本次项目证明了关键闭环，但不能把客户这次看到的形态直接当成我们未来软件工厂的全部定义。

## 2. 三层复盘框架

页面标题：

本次复盘分三层看

页面主文案：

第一层：客户理解口径  
客户希望软件工厂完成自然语言、多轮澄清、多 agent 协作、真实数据接入和应用生成。

第二层：本次交付验证  
电子云验证了自然语言到应用、本体数据接入、真实数据展示和客户系统嵌入。

第三层：产品主张  
电子云软件工厂长期核心是多 agent 管理协作、任务分发执行、领域能力包沉淀和云产品能力底座融合。

建议视觉：

三层金字塔或三段式横向结构。

讲稿备注：

客户口径是重要输入，但不是全部产品定义；交付验证说明我们当前站在哪里；产品主张回答下一步往哪里走。

## 3. 客户真正关心什么

页面标题：

客户关注的是全过程可信，而不只是生成代码

页面主文案：

客户本次关注的软件工厂能力，可以归纳为六项：

- 需求理解与澄清：准确理解业务场景，主动提出澄清项，持续让用户确认。
- 数据接入与数据流转：讲清数据来源、处理过程、进入 agent/LLM 的方式和应用展示结果。
- 方案设计可控：关键方案可人工调整，不由模型黑箱主导。
- 多 agent 协作可视化：执行前看协作图，执行中看状态、产物和失败重试。
- 最终应用质量：界面效果好，真实数据驱动，贴合客户系统，可嵌入。
- 自我进化与能力沉淀：能沉淀 agent、skills 和过往经验。

页面补充：

客户提供的航母相关场景共同暴露出强领域业务理解、外部数据接入、判断规则转应用逻辑、复杂前端表达和领域能力沉淀要求。

建议视觉：

六宫格能力图，底部补一行“客户场景 -> 领域能力包”。

讲稿备注：

这些场景不是普通页面生成需求，而是在测试软件工厂的领域知识、数据接入、规则研判和应用表达能力。

## 4. 本次交付验证与现场观察

页面标题：

电子云证明了闭环可用，但过程可信还要加强

页面主文案：

本次电子云已验证：

- 自然语言描述生成应用的整体流程跑通。
- 本体数据源已对接。
- 生成应用能够调用本体数据源展示真实数据。
- 界面样式贴合客户系统。
- 生成应用具备嵌入客户系统的便利性。

现场厂商观察：

| 厂商 | 客户感知优势 |
| --- | --- |
| 领铄 | 需求分析交互、澄清项识别、数据源处理过程可视化更容易被客户感知 |
| 电子云 | 真实数据应用生成闭环、客户系统嵌入能力、与电子云产品结合空间 |
| 15 所 | 工程链路直接，但产品化展示和用户体验不足 |

页面结论：

领铄更容易让客户看到“过程可信”；电子云本次更明确证明了“闭环可用”。

建议视觉：

上半部分闭环流程图，下半部分三列厂商观察。

讲稿备注：

这里不要讲厂商输赢。重点是识别客户认可能力差距：我们已经证明闭环，但还要把需求澄清、数据流转和 agent 协作过程做得更可见。

## 5. 下一步升级方向

页面标题：

从闭环可用升级为过程可信、产物稳定、能力可沉淀

页面主文案：

电子云下一阶段需要补齐四个方向：

- 过程可信：需求澄清、数据流转、agent 协作过程可见。
- 产物稳定：生成应用质量、真实数据接入、部署验证更稳定。
- 能力可沉淀：领域经验、skills、subagent、应用蓝本可复用。
- 工程可进入：agent 产物进入 DevOps、低代码、微服务、网关、观测等工程系统。

客户高感知优先级：

1. 数据流转可视化。
2. 需求澄清与推荐收敛。
3. 多 agent 协作执行图与状态。
4. 生成应用效果和嵌入能力。
5. 自我进化与 skills 沉淀展示。

建议视觉：

从“闭环可用”到四个升级方向，右侧放客户感知优先级阶梯。

讲稿备注：

数据流转可视化应放第一优先级。客户最容易质疑的是数据是否真实、数据怎么来、怎么处理、怎么进入分析、最终怎么展示。

## 6. 电子云软件工厂产品主张

页面标题：

软件工厂不是 demo 生成器，也不是云产品的 AI 包装层

页面主文案：

电子云软件工厂的长期主张：

以多 agent 管理协作、任务分发执行、领域能力包沉淀为核心，通过 agent、skills、subagent 的持续扩展和高度编排，结合自身云产品完成真实工程生产。

核心对象：

- agent
- skills
- subagent
- 任务
- 编排
- 领域知识
- 产物

能力支撑：

- 软件工厂工作台。
- 领域能力包沉淀。
- Agent/Skills 市场。
- 云产品能力底座。

建议视觉：

中心是“多 agent 管理协作与任务分发执行”，周围四个能力支撑。

讲稿备注：

应用生成是重要入口，但不是终局。真正的主轴是 agent 能力如何被管理、编排、分发、沉淀，并进入真实工程生产链路。

## 7. Agent 组织方式与能力市场

页面标题：

默认生产主链路 + 动态扩展专业 agent + 能力市场

页面主文案：

默认生产主链路：

- 需求分析。
- 测试设计。
- 方案设计。
- 代码生成。
- 测试生成。
- 测试验证。
- 代码审查。
- 部署交付。
- 观测回写。

动态扩展专业 agent：

- 领域知识 agent。
- 系统集成 agent。
- 数据接入 agent。
- 安全审查 agent。
- 低代码 agent。
- 网关集成 agent。
- 微服务 agent。
- 观测 agent。

能力市场：

- 协作智能体市场负责 agent 能力发现、分发、安装和治理。
- Skills 市场负责领域知识、工具调用方法、云产品适配、代码生成规范、数据接口契约等 skills 分发。
- 本地能力库负责当前租户或项目已安装、启用、可治理、可进入任务参与计划的能力资产。

建议视觉：

左侧主链路，中间动态 agent，右侧 agent/skills 市场和本地能力库。

讲稿备注：

未来软件工厂不能是固定 agent 流水线。市场负责发现和分发，库负责本地可用和治理，这样软件工厂才能持续扩展。

## 8. 领域能力包与云产品能力底座

页面标题：

让软件工厂越交付越强，并进入真实工程链路

页面主文案：

领域能力包沉淀：

- 领域知识。
- 数据接口契约。
- 判断规则和研判参数。
- skills。
- subagent。
- 应用蓝本。
- 验收口径。
- 可观测指标。

云产品交互场景：

- DevOps：需求、任务、代码仓库、流水线、制品、部署记录。
- 低代码：表单、流程、报表、管理页面。
- 微服务：服务接口、注册、治理和调用。
- 网关：API 暴露、鉴权、限流和路由。
- 观测：日志、指标、链路追踪、告警和质量看板。

页面结论：

领域能力包让软件工厂越交付越强；云产品能力底座让 agent 工作进入可治理、可审计、可运行的工程资产体系。

建议视觉：

左侧“交付经验 -> 领域能力包 -> 后续复用”，右侧“agent -> 云产品能力底座 -> 工程资产”。

讲稿备注：

云产品不是被 AI 包装，而是成为 agent 可以调用、写入、消费、治理和观测的能力底座。

## 9. 第一阶段优先闭环与技术边界

页面标题：

先打通 DevOps，同时守住数据链路边界

页面主文案：

DevOps 第一阶段最小闭环：

1. 需求分析 agent 生成需求规格说明书，并拆成 DevOps 需求项/任务项。
2. 测试设计 agent 根据需求项生成测试用例，并写入 DevOps 测试管理能力。
3. 代码生成 agent 在对应项目仓库提交代码。
4. 测试生成 agent 在代码生成后生成自动化测试脚本。
5. 测试验证/部署 agent 触发或更新流水线。
6. 部署结果、制品地址、应用访问地址回写 DevOps。
7. 软件工厂工作台反向展示 DevOps 链接和状态。

关键技术边界：

- 生成期数据链路：需求澄清、数据接入、接口验证、字段抽取、数据契约、下游生成约束。
- 运行期数据链路：生成应用通过 API、网关、本体服务、代理、鉴权配置获取真实数据，并负责展示、刷新、异常提示和降级。
- factory-server 不应成为所有业务应用的通用数据查询网关。

建议视觉：

上半部分 DevOps 闭环流程；下半部分生成期/运行期数据链路分栏。

讲稿备注：

DevOps 是第一阶段最优先打通对象，因为它承接软件生产主链路。与此同时，数据职责必须分清，否则软件工厂后端容易变成业务数据中台。

## 10. 边界与决策

页面标题：

明确边界，并形成下一阶段建设决策

页面主文案：

非目标和边界：

- 不把 630 客户口径等同于电子云软件工厂终局。
- 不把软件工厂做成固定 agent 流水线。
- 不把软件工厂做成单纯应用 demo 生成器。
- 不把云产品融合写成 AI 包装。
- 不把 factory-server 做成所有业务数据的通用查询网关。

建议形成五项决策：

1. 第一阶段产品边界：哪些能力进入软件工厂工作台。
2. DevOps 最小闭环：需求项、测试用例、代码仓库、测试脚本、流水线、部署记录是否作为第一阶段必做。
3. 市场能力范围：agent 市场和 Skills 市场是否先做轻量可演示版。
4. 数据流转可视化：是否作为下一次客户演示第一优先级。
5. 领域能力包：是否以本次航母相关场景作为首批沉淀样本。

建议视觉：

左侧五条边界，右侧五项决策清单。

讲稿备注：

最后要把汇报收束到可决策事项上。复盘不应停留在观点，而应推动下一阶段建设边界和优先级落地。
